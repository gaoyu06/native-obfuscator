# Automated-analysis quality evaluation

## Scope

This document defines methodology only. No evaluation has been run and no
readability, maintainability, security, or analysis-resistance result is
claimed.

The subject is software-quality evaluation of generated artifacts: how reliably
automated static analyzers and LLM-based code readers can recover, explain,
trace, and review behavior. A low comprehension score is not evidence of
security; it may instead indicate poor debuggability, hidden defects, or a bad
benchmark.

## Research questions

Measure these separately:

1. **Buildability:** Can standard C++ tooling parse, index, compile, and diagnose
   the artifact?
2. **Structural recovery:** Can an analyzer recover functions, control-flow
   edges, call edges, data types, exception paths, and Java/native boundaries?
3. **Functional comprehension:** Can it identify inputs, outputs, invariants,
   edge cases, and the implemented operation?
4. **Traceability:** Can it map an observed C++ operation or failure back to the
   Java class/method/bytecode offset and vice versa?
5. **Defect detection:** Can it locate seeded, realistic correctness/resource/
   JNI-lifetime defects and distinguish clean controls?
6. **Change quality:** Can it propose a bounded fix that compiles and passes
   hidden tests without unrelated edits?
7. **Review efficiency:** What wall time, machine resources, model tokens, and
   monetary cost are required?

Do not collapse these into one “readability” or “resistance” number without a
human-approved weighting and full component disclosure.

## Artifact variants

For each corpus item, build paired artifacts from the same source and compiler
commit:

| Variant | Purpose |
|---|---|
| Java source and bytecode reference | Establish source-level and `javap` baselines |
| Current snippet-generated C++ | Migration control while the old backend exists |
| IR structured-C++ debug output | Measure maintainable names, comments, source maps, and manifest |
| IR structured-C++ release output | Measure normal optimization/stripping policy |
| Optional interpreter runtime plus instruction tables | Compare a second compiler backend, not a packing scheme |
| Hand-written equivalent C++ where feasible | Calibrate language/tool familiarity independently of translation |

Debug and release variants must come from the same IR. Record whether names,
comments, line directives, source maps, symbols, and manifests are present.
Do not compare a fully annotated candidate with a stripped baseline and call the
difference a backend effect.

## Corpus construction

Use three sources:

- small generated programs with exhaustive or property-based semantic oracles;
- repository compatibility fixtures covering arithmetic, control flow, arrays,
  strings, exceptions, monitors, class initialization, indy, and SDK calls;
- licensed, immutable real-world methods selected by documented criteria.

Stratify by bytecode count, control-flow complexity, exception edges, reference
operations, JNI calls, generated C++ size, and domain. Keep algorithm families
in only one of development, calibration, or held-out test sets. Deduplicate
near-identical methods by normalized bytecode hash.

Record provenance, license, source revision, selection query, and exclusions.
Private customer code is excluded unless a human approves handling, retention,
and analyzer-provider terms.

### Gold data

Gold answers come from executable behavior and compiler metadata where
possible:

- CFG and call edges from the verified IR;
- Java/C++/interpreter source maps generated by the compiler;
- typed inputs, outputs, and declared effects from fixture specifications;
- expected outputs/exceptions from differential tests;
- seeded defect identity and affected location from a deterministic mutation
  manifest;
- patch acceptance from compile, static checks, and hidden semantic tests.

Human-authored semantic rubrics require two independent reviewers, adjudication,
and an agreement report. The model under evaluation never writes its own key.

## Task suite

Each task has a frozen prompt/schema, permitted tools, timeout, and machine-
checkable output where possible.

1. **Function summary:** identify purpose, inputs, output, side effects,
   exceptions, and uncertainty in a structured schema.
2. **Output prediction:** predict results for held-out boundary inputs; score
   against execution.
3. **Graph recovery:** emit CFG/call/data-dependency edges using stable artifact
   identifiers; score precision, recall, and F1 against IR-derived gold.
4. **Cross-boundary trace:** locate every JNI/SDK operation and map it to Java
   method and bytecode offsets.
5. **Invariant and edge-case review:** select applicable invariants from a
   closed taxonomy and cite artifact spans.
6. **Defect localization:** rank locations for one seeded defect or state that
   the control is clean. Include clean controls to measure false positives.
7. **Patch task:** produce a minimal change. Score only by compile/static/
   hidden-test outcome, patch scope, and regression count; prose plausibility is
   insufficient.
8. **Unsupported-feature diagnosis:** explain a compiler refusal using the
   structured diagnostic and artifact manifest.

Seeded defects model ordinary compiler/runtime quality issues such as wrong
integer corner semantics, a missed exception edge, output-size validation, or
JNI reference cleanup. They are introduced only into isolated evaluation
artifacts and never into release code.

## Analyzer matrix

### Deterministic baselines

Run the same pinned toolchain on every C++ variant:

- parser/indexer success and diagnostics;
- compiler warnings at the project policy level;
- `clang-tidy` checks selected before seeing results;
- CFG/call-graph extraction;
- ASan/UBSan and JNI-check findings for executable fixtures;
- complexity, source size, symbol count, and source-map coverage.

Tool versions, checks, compilation database, flags, target triple, and exit
status are captured. Static tools are baselines, not ground truth for Java
semantics.

### LLM-based readers

Use at least two pinned model/configuration families when policy permits.
Record:

- provider, exact model/version or immutable deployment digest, date, region,
  and retention/training policy;
- system/user prompt digests, temperature/sampling parameters, context limit,
  seed where supported, and number of repetitions;
- whether the model sees one function, translation unit, full project, IR,
  manifest, source map, compiler output, or execution tools;
- tool-call policy and all tool outputs;
- input/output token count, latency, failures, and cost.

Run a no-tools condition and a production-relevant tools condition separately.
Never let one variant receive compiler execution or source maps that another
variant lacks. Randomize artifact order and opaque identifiers so the evaluator
cannot infer the backend from filenames.

Source comments and string literals are untrusted evaluation data. The harness
delimits them from instructions, records any instruction-following deviation,
and includes benign contamination controls. It does not execute model-produced
commands outside the disposable sandbox.

Because hosted models can change, repeat the pinned suite at release evaluation
time. Results name the model/date and are not generalized to “LLMs.”

## Metrics

| Dimension | Metrics |
|---|---|
| Buildability | parse/index/compile success; diagnostic count by severity; sanitizer/JNI-check findings |
| Structural recovery | edge/node precision, recall, F1; type accuracy; source-map top-1/top-k accuracy |
| Comprehension | field-level exact/F1 scores; rubric score with cited evidence; calibrated abstention/error rate |
| Defect detection | localization top-k, mean reciprocal rank, true/false-positive rates, clean-control specificity |
| Patch quality | compile rate, hidden-test pass rate, regression count, changed lines/files, static-check delta |
| Efficiency | wall/CPU time, peak memory, tokens, tool calls, and cost |
| Reproducibility | run failure rate and within-configuration variance |

Report distributions and paired differences, not only means. Missing, refused,
truncated, unparsable, and timed-out responses remain separate outcome classes;
they are not silently scored as ordinary wrong answers.

## Experimental controls

- Use the same semantic corpus and target triple for paired backend comparisons.
- Normalize only non-semantic build paths/timestamps; preserve identifiers that
  are part of a real artifact mode.
- Stratify or match on artifact token/byte length so context truncation is not
  mistaken for semantic opacity.
- Include source-name/comment ablations to measure how much traceability comes
  from metadata.
- Include hand-written C++ controls to measure generic C++ difficulty.
- Keep prompts and task keys frozen before running release candidates.
- Keep held-out keys inaccessible to the model runner and report any suspected
  benchmark contamination.
- Use disposable, network-restricted execution for generated patches.
- Verify every candidate artifact passes semantic equivalence before using it
  in readability comparisons; broken output is not a valid “harder to analyze”
  result.

## Statistical plan

Choose sample size and primary metrics before observing candidate results. Use
paired analysis by source method. Report effect sizes and bootstrap confidence
intervals; account for repeated model samples and method families with a
hierarchical or clustered analysis. Correct for multiple comparisons when
claiming differences across many tasks/backends.

Publish exclusions and failures. A result is inconclusive when intervals are
wide, model drift is detected, corpus coverage is insufficient, or a
confounder such as artifact size explains the difference.

This document intentionally contains no example scores or expected direction.

## Reproducible run record

Each run emits append-only JSONL plus referenced artifacts:

```json
{
  "schema": 1,
  "corpus_id": "opaque-id",
  "source_digest": "sha256:...",
  "artifact_digest": "sha256:...",
  "backend": "cpp-debug",
  "compiler_commit": "...",
  "toolchain": {"name": "...", "version": "...", "flags": ["..."]},
  "task": {"id": "...", "prompt_digest": "sha256:...", "key_digest": "sha256:..."},
  "analyzer": {"kind": "static-or-llm", "identity": "...", "config_digest": "sha256:..."},
  "permissions": {"source_map": false, "execution": false, "network": false},
  "outcome": "complete",
  "metrics": {},
  "raw_output_digest": "sha256:..."
}
```

The actual schema includes environment, timing, resource, retry, and failure
fields. A report is generated from these records; manually transcribed model
answers or scores are not accepted.

## Review and interpretation gates

Before the harness runs, human review approves dataset licenses/privacy,
research questions, primary metrics, task keys, analyzer data policy, and
statistical plan. Before publication, reviewers inspect random samples,
adjudication, failures, and report generation from raw records.

Acceptable conclusions are narrow, for example: “under analyzer configuration
X and task set Y, debug artifact A improved source-map top-1 accuracy relative
to B.” Unacceptable conclusions include “cannot be understood,” “resists AI,”
or “is secure” unless a separately designed and evidenced security evaluation
supports them.
