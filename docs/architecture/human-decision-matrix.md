This matrix separates decisions that change product promises or risk ownership
from implementation work that can be prepared autonomously. “Recommendation”
is the default for planning, not an approval.

| ID | Decision | Options | Recommendation | Main risk | Why a human might override |
|---|---|---|---|---|---|
| D1 | Production Java baseline | 8, 11, 17, or 21 | JDK 17 runtime and class-file 61 as the first required baseline; keep 8/11 as separately tested legacy profiles and 21/25 as promotion candidates | A higher floor can exclude existing users; a lower floor delays modern correctness work and SDK design | Customer deployment data or an existing compatibility contract may require JDK 8/11, or an organization may mandate JDK 21 |
| D2 | Meaning of “JDK support” | Parser-only, transpiler-host, generated-JAR runtime, input class-file features, or all | Publish all dimensions separately; call a version supported only when its declared feature corpus and native targets pass | A single “supports JDK N” badge hides unsupported attributes, bootstraps, packaging, or runtime behavior | Marketing may want simpler tiers, but must accept a documented reduced definition |
| D3 | Output class-file version | Always 52, always latest, preserve input, or lower only with a proven transform | Preserve each input class's version and attributes; reject unsupported semantics. Add explicit downleveling only as a separate verified feature | Preserving versions requires newer runtime profiles; blind downleveling can produce invalid classes or changed access semantics | A controlled Java-8-only deployment may prefer a real, separately implemented downleveler |
| D4 | Core IR form | Linear stack IR, typed CFG with block parameters, full SSA/sea-of-nodes, or external Jimple | Begin with verifier-aware typed CFG/block parameters; add SSA only for eligible optimization regions | Too little structure repeats current bugs; premature global SSA complicates exceptions, uninitialized values, and monitors | A team with proven JVM SSA infrastructure may choose it if it demonstrates the required semantic model |
| D5 | IR implementation dependency | ASM analysis plus in-house IR, SootUp/Jimple, LLVM/MLIR frontend, or another framework | Keep ASM parsing and build a small project-owned semantic IR; prototype alternatives against the corpus before adoption | In-house semantics are substantial work; a framework adds size, version lag, and semantic adaptation cost | Maintainers may already operate and support SootUp/LLVM and accept its dependency/toolchain footprint |
| D6 | First backend | Structured C++, interpreter, LLVM, or WASM | Structured C++ vertical slice first; interpreter second over the same stable IR | C++ has undefined-behavior traps; interpreter-first can lock the IR to one-opcode dispatch and defer the main product path | Code-size or portability may be more urgent than native performance, provided the direct backend remains funded and gated |
| D7 | Legacy snippet backend during migration | Remove immediately, keep indefinitely, or temporary explicit fallback | Keep only as a temporary non-default comparison/fallback, then delete it when the supported-op parity gate passes | Immediate removal raises migration risk; indefinite fallback doubles semantics and masks unsupported input | A security or correctness finding may require disabling the old backend before parity |
| D8 | Unsupported method policy | Silent Java fallback, old backend fallback, fail whole build, or per-method refusal report | Default to fail with precise diagnostics for explicitly selected methods; allow an explicit Java fallback profile recorded in the manifest | Fail-closed interrupts builds; fallback may violate user expectations about what became native | A compatibility-oriented product tier may knowingly prefer Java fallback and expose it in policy/reporting |
| D9 | Primary Java/native binding | JNI, FFM, JNA/JNR, or dual | JNI is the JDK 17 baseline; use a stable C ABI so a separate JDK 22+ FFM adapter can be added | JNI is unsafe and restricted native access warns on JDK 24+; dual adapters increase tests | A JDK 22+-only product may choose FFM first; embedded/custom JVM customers may require JNI only |
| D10 | FFM packaging | Multi-release JAR, separate adapter artifact, generated binding, or no FFM | Separate adapter artifact to prevent JDK 17 verification/linkage accidents and keep preview APIs out | Extra artifact complicates distribution and version alignment | A mature MR-JAR release process may make one artifact more valuable than isolation |
| D11 | SDK invocation model | Explicit Java API, annotation, bytecode signature recognition, or transparent JDK API replacement | Explicit API first; a reviewed annotation may follow. Do not infer algorithm identity from arbitrary bytecode | Explicit adoption requires source/bytecode changes; automatic replacement can silently change provider, errors, side channels, or results | A closed, compiler-generated corpus may permit exact, versioned intrinsics with proof and fallback |
| D12 | SDK v1 primitives | Encoding only; hash/encoding; AEAD; raw memory; broad utility set | Start with hex/Base64, SHA-256, and constant-time byte equality plus ABI/capabilities. Defer AEAD, streaming state, raw pointers, and native allocation | Even small crypto-adjacent APIs need input/error/side-channel review; broad v1 freezes poor contracts | A concrete customer workload and security team may prioritize another standardized primitive |
| D13 | Crypto implementation/provider | Vendor audited source, dynamically use system provider, platform providers, write in-house, or omit crypto | Do not write crypto. Choose one reviewed, pinned implementation after license, provenance, CVE/update, target, and side-channel evaluation | Vendoring creates update duty and binary size; system providers vary by machine; wrong choice creates security liability | Enterprise policy may mandate OpenSSL/FIPS or prohibit vendored code; minimal distributions may require a portable source dependency |
| D14 | JNI array/string access | Always copy, critical pin, direct buffer, or size-based hybrid | Copy by default; direct buffers for caller-controlled zero-copy; critical access only for short bounded kernels proven by tests and benchmarks | Copying costs throughput; critical regions can harm GC and disallow blocking/JNI activity | A controlled collector/workload with measured bounds may justify a pinning policy |
| D15 | String semantics | UTF-8, modified UTF-8, UTF-16 code units, or internal compact-string access | Specify Java UTF-16 code-unit behavior at the API; use standard JNI access and explicit RFC encoders; never inspect private compact-string layout | Unicode conversions can change malformed-surrogate behavior; pinning has runtime risks | A byte-oriented SDK API may standardize UTF-8 instead, with an explicit Java conversion contract |
| D16 | Interpreter backend default | Off, per-method opt-in, automatic fallback, or default | Off by default; explicit per-build/per-method selection with manifest and resource limits | Dispatch can be slow and enlarge the trusted runtime; automatic fallback can hide compiler gaps | A code-size-focused edition may make it default after independent compatibility/performance gates |
| D17 | Interpreter format stability | Internal-only, versioned but unstable, or public compatibility contract | Version it for rejection/diagnostics, but keep it internal and regenerate with each build | Unversioned tables risk crashes; public stability constrains compiler evolution | Tooling partners may need a documented format and accept long-term compatibility cost |
| D18 | Native targets/toolchains | Current OS/JDK matrix, reduced tier-1 set, Zig-only, CMake-only, or both | Define tier 1 initially as x86-64 Linux/Windows/macOS with CMake native compilers; validate Zig separately before treating cross-built artifacts as equivalent | A broad matrix multiplies ABI, loader, sanitizer, and signing work; a narrow matrix excludes users | Usage telemetry may prioritize arm64, or the team may have stronger Zig than host-toolchain infrastructure |
| D19 | Performance release policy | No threshold, absolute threshold, relative-to-Java threshold, or regression budget | Establish repeatable baselines first; then approve workload-specific correctness-first regression budgets, never one global speedup target | Thresholds can be noisy or gamed and may favor microbenchmarks over user workloads | Service-level objectives or hardware contracts may provide meaningful absolute limits |
| D20 | Automated-analysis evaluation | Static tools only, local models, hosted models, human study, or combinations | Use deterministic static baselines plus at least two pinned analyzer configurations; add blinded human calibration on a licensed subset | Hosted inputs may leak code; model drift breaks comparisons; task contamination inflates scores | Privacy rules may require local-only evaluation, or cost may restrict the initial provider set |
| D21 | Meaning of analyzer “quality” | Readability, functional comprehension, traceability, defect detection, or resistance | Measure each separately and report scores with uncertainty; do not combine them into a resistance claim | A composite score hides trade-offs and can be mistaken for security evidence | A product dashboard may need a composite, but weights and limitations require explicit approval |
| D22 | Generated artifact readability | Optimize for maintainers, deliberately minimize, offer modes, or ignore | Produce deterministic readable debug artifacts and optimized release artifacts from the same IR; keep source maps/manifests for both | Debug metadata can expose implementation detail; unreadable output harms support and audit | A distribution policy may strip debug material from shipped artifacts while retaining secured build artifacts |
| D23 | Native-access configuration on modern JDKs | Ignore warning, launcher flag, executable-JAR manifest, module-specific enablement, or deny unsupported | Document module-specific enablement where possible; test JDK 24/25 both with normal warnings and `--illegal-native-access=deny` | Future JDK defaults can turn warnings into failures | Deployment tooling may standardize `ALL-UNNAMED` or a manifest for operational simplicity |
| D24 | Production release authority | Automated green gates only or named compiler/security/release owners | Require named human sign-off after automated gates on the exact release artifact | Manual approval can slow release; automation cannot accept API/security/residual-risk ownership | A mature organization may formalize delegated approval, but ownership still must be explicit |
